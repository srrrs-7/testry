# 完了報告（仕様 23 章の形式）

報告は日本語。**実行していない検証を成功と書かない**ことが最優先。

## 書く前に確かめる

1. `make ci` を最後まで実行し、exit code と件数を控える（途中の実行結果を流用しない）。
2. `git status --short` と `git diff --stat` で、変更したファイルを実物から列挙する。
3. `docs/acceptance.md` が今回の変更を反映しているか（新しいテスト名、状態）。
4. ミューテーション確認で壊した実装が残っていないか。
5. 計測値を載せるなら、`docs/benchmarks/` に生データがあるか（skill `bench`）。

## 形式

```markdown
### Implemented
実装したものを、利用者から見た挙動で書く。

### Changed files
主なものを、新規と更新に分けて。依存を足した・版を変えた場合は必ず書く。

### Tests executed
実行したコマンド、exit code、クレートごとの件数。ミューテーション確認の内容と結果。
見つけて直した不具合があれば書く。

### Tests not executed
実行していない検証を、理由つきで（別アーキテクチャ、実プロジェクト、未確認のブラウザなど）。

### Known limitations
利用者が踏む順に。回避方法があれば添える。

### Measured performance
実際に測った値だけ。条件（ビルド種別、回数、fixture）と、何の効果なのかを書く。測っていなければ「未計測」。

### Next
次の候補。利用者の判断が要るものは、そう書く。
```

## 書き方

- 結論を先に書く（どこまで完了し、ゲートは通ったか）。
- 失敗・未完了・迂回したことを、成功と同じ目立ち方で書く。次のようなものは必ず伝える:
  - 仕様と違う実装にした箇所と、その理由（ADR の番号）
  - 利用者の指示で対象外にした受け入れ条件（「検証済み」とは書かない）
  - 作業中に起きた想定外のこと（外部への送信、意図しないファイルの変化、ルールに反した操作）
- 「高速化した」とだけ書かない。実行対象を減らした効果と、オーケストレーションの負荷を分けて書く。
- 件数や時間は、控えた実測値をそのまま使う。丸めて良く見せない。
- コミットは、利用者に頼まれたときだけ行う。
