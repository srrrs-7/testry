# ベンチマーク

## 実行

```bash
make bench                                   # release ビルド → scripts/bench.ts。ネットワーク遮断
BENCH_RUNS=10 BENCH_SIZES=100,1000 make bench   # 試走用に軽くする
```

- 既定はウォームアップ 3 回のあと 30 回、規模は 100 / 1,000 / 5,000 モジュール。
- 結果は `docs/benchmarks/` に、日付つきの 3 ファイルで出る:
  `raw-<date>.jsonl`（1 行 1 サンプル）、`summary-<date>.json`、`environment-<date>.json`。
- スクリプトはコンテナ内の Bun で動く。ホストで `bun` / `node` を使わない。
- 計測中は、同じマシンで他の重い処理（イメージのビルド、別のゲート）を走らせない。

## 結果を文書にする

`docs/benchmarks.md` を、生データの要約として更新する。

- **実際に計測した値だけ**を載せる。表の数値は `summary-<date>.json` と一致させる。
- 計測日・環境・条件（release ビルド、回数、fixture の構成、キャッシュの状態）を書く。
- 過去の生データは消さない（比較の根拠になる）。古い計測を置き換えるときは、どの日付の値かを明記する。
- 「計測していないもの」の節を保つ（実プロジェクト、ブラウザ系 suite、冷えたキャッシュ、他のマシン）。

## 読み方の注意（過去に取り違えかけた点）

- **同じ仕事どうしを比べる。** Vitest を既定の worker 数で直接実行した値と、`workers = 1` の suite を
  testry 経由で実行した値を比べると、設定の差（約 0.7 秒）をオーケストレーションの負荷と見誤る。
- **実行対象を減らした効果と、testry 自体の速さを分ける。** affected が full より速いのは、走らせるテストが
  減ったからであって、Rust で書いたからではない。
- 対象が 1 ファイルだけのときは testry の固定費（計画、版の確認、前後のスナップショット、成果物と履歴の書き込み）が
  目立つ。直接実行より遅い値も、そのまま載せる。
- 30 回では p95 は目安にしかならない。差が分布の重なりの範囲なら「差がある」と書かない。
- 合成リポジトリの値を、実プロジェクトの見込みとして書かない。

## 前の計測と比べるとき

同じ環境（`environment-<date>.json` の CPU、メモリ、各版）で取った値どうしだけを比べる。
p50 の差がばらつき（最小–最大の幅）より小さければ「変化なし」とする。
悪化していたら、内訳（snapshot / analysis / selection、計画 / 検証）のどこが増えたかを示す。
