# ベンチマーク

仕様 20 章の計測。**実際に計測した値だけ**を載せる。改善倍率の約束はしない。
生データは [`docs/benchmarks/`](benchmarks/) にあり、ここの表はその要約である。

- 計測日: 2026-11-17（UTC）
- 生データ: [`raw-2026-11-17.jsonl`](benchmarks/raw-2026-11-17.jsonl)（1 行 1 サンプル、510 行）
- 要約: [`summary-2026-11-17.json`](benchmarks/summary-2026-11-17.json)
- 環境: [`environment-2026-11-17.json`](benchmarks/environment-2026-11-17.json)
- 再実行: `make bench`（コンテナ内、ネットワーク遮断。設定は `BENCH_RUNS` / `BENCH_WARMUP` / `BENCH_SIZES`）

## 環境と条件

| 項目 | 値 |
|---|---|
| 実行場所 | このリポジトリの開発イメージのコンテナ（Colima の Linux VM 上、linux-aarch64、kernel 6.8.0-147） |
| CPU / メモリ | 8 コア / 約 11.7 GiB（VM に割り当てられた分） |
| testry | 0.1.0、**release ビルド** |
| Rust / Bun / Node / Vitest / Git | 1.100.0 / 1.4.4 / 26.13.1 / 5.1.0 / 2.47.3 |
| ネットワーク | 遮断（計測に取得は含まれない） |
| キャッシュ | OS のファイルキャッシュは温まった状態。testry 自身は run をまたぐキャッシュを持たない。Warm Pool は存在しない |
| 回数 | 各計測ともウォームアップ 3 回のあと 30 回。p50 / p95 は nearest-rank |

計測値の意味:

- **wall**: コマンドの開始から終了までの実時間。
- **最大 RSS**: そのコマンドのプロセスツリーの中で、**最も大きかった 1 プロセス**の最大常駐メモリ（合計ではない）。
  `plan` では testry 自身、実行系ではランナー（Node）の値になる。
- **CPU**: そのコマンドと、それが待ち合わせた子孫プロセスの user + system 時間の合計。

## 1. 計画（`testry plan`）の規模特性

合成リポジトリ: ソース 10 個が import で数珠つなぎになった鎖を並べ、鎖ごとにテスト 1 つ。
「モジュール数」はテスト以外のソース数で、ファイル総数はその 1.1 倍。

| モジュール数（ファイル数） | 計測 | wall p50 | wall p95 | 最大 RSS p50 | 内訳 p50（snapshot / analysis / selection） |
|---|---|---|---|---|---|
| 100（110） | `plan --mode full` | 4.3 ms | 5.0 ms | 20.9 MiB | 2 / 0 / 0 ms |
| 100（110） | `plan`（affected、変更なし） | 8.4 ms | 9.7 ms | 24.1 MiB | 5 / 1 / 0 ms |
| 100（110） | `plan`（affected、1 モジュール変更） | 9.1 ms | 9.8 ms | 25.1 MiB | 5 / 1 / 0 ms |
| 1,000（1,100） | `plan --mode full` | 7.5 ms | 9.6 ms | 26.6 MiB | 5 / 0 / 0 ms |
| 1,000（1,100） | `plan`（affected、変更なし） | 21.1 ms | 23.1 ms | 29.7 MiB | 13 / 5 / 0 ms |
| 1,000（1,100） | `plan`（affected、1 モジュール変更） | 23.3 ms | 28.9 ms | 30.5 MiB | 13 / 6 / 0 ms |
| 5,000（5,500） | `plan --mode full` | 24.0 ms | 26.9 ms | 33.5 MiB | 21 / 0 / 0 ms |
| 5,000（5,500） | `plan`（affected、変更なし） | 82.3 ms | 116.0 ms | 33.5 MiB | 50 / 28 / 0 ms |
| 5,000（5,500） | `plan`（affected、1 モジュール変更） | 86.6 ms | 123.6 ms | 33.8 MiB | 51 / 27 / 3 ms |

読み取れること:

- 5,500 ファイルで affected の計画は p50 87 ms、p95 124 ms。ファイル数にほぼ比例して伸びている。
- 時間の 6 割は snapshot（Git の列挙と差分、内容の指紋）で、解析（Oxc での構文解析と import 解決）が 3 割。
  グラフ探索と plan の組み立ては数 ms 以下。
- affected は基準版と現在版の 2 つのグラフを作るので、full（グラフを使わない）の 2〜4 倍かかる。
- 解析結果のディスクキャッシュは実装していない。この規模では不要と判断した（ADR-0007 の 7）。
- **選択の精度**: 鎖の末端を 1 つ変更したとき、選ばれたテストは 1 ファイル（5,000 モジュールの場合 500 ファイル中 1）、
  fallback は 0 件だった。合成データなので、実プロジェクトの fallback 率（未解決 import や `global_inputs` による拡大）は
  これより高くなる。

## 2. 実行: 直接実行 / `testry verify` / `testry test`

合成リポジトリ: Bun のテスト 40 ファイル（各 5 件）と Vitest のテスト 20 ファイル（各 5 件）、計 60 ファイル・300 件。
テストの中身はごく軽い（＝ランナーの起動とオーケストレーションの比率が最も大きく出る条件）。

| 計測 | 実行したテストファイル | wall p50 | wall p95 | 最小–最大 | CPU p50 |
|---|---|---|---|---|---|
| ランナーを直接、全体（`bun test`; `vitest run --maxWorkers=1`） | 60 | 1,131 ms | 1,258 ms | 1,018–1,277 ms | 1,425 ms |
| `testry verify`、suite を 1 つずつ | 60 | 1,171 ms | 1,275 ms | 1,080–1,300 ms | 1,457 ms |
| `testry verify`、suite を 2 つ同時 | 60 | 1,145 ms | 1,250 ms | 1,093–1,255 ms | 1,446 ms |
| ランナーを直接、全体（Vitest は既定の worker 数） | 60 | 398 ms | 462 ms | 349–516 ms | 1,843 ms |
| バージョン確認だけ（`bun --version`; `vitest --version`） | — | 23 ms | 28 ms | 20–29 ms | 27 ms |
| ランナーを直接、影響する 1 ファイルだけ（`bun test ./src/f7.test.ts`） | 1 | 2.1 ms | 3.4 ms | 1.8–3.9 ms | 2.4 ms |
| `testry test`（affected、1 モジュール変更） | 1 | 39.8 ms | 53.8 ms | 37.4–55.1 ms | 43.6 ms |
| `testry verify`（同じ変更のまま全体） | 60 | 1,144 ms | 1,227 ms | 1,074–1,233 ms | 1,432 ms |

`testry verify`（1 つずつ）の内訳 p50: 計画 3 ms、検証 1,158 ms（うち Bun の suite 10 ms、Vitest の suite 1,113 ms）、合計 1,163 ms。
`testry test`（affected）の内訳 p50: 計画 9 ms、検証 15 ms（うち Bun の suite 2 ms）、合計 28 ms（プロセス全体の wall は 39.8 ms）。

### オーケストレーションの追加負荷

同じ仕事（同じ worker 数）で比べると、`testry verify` はランナーの直接実行より p50 で **約 40 ms（3.5%）遅い**
（1,171 ms 対 1,131 ms）。ただし両者の分布は重なっており（直接実行の p95 は 1,258 ms）、この差は計測のばらつきと
同じ程度の大きさである。内訳として分かっているのは、実行前のバージョン確認が約 23 ms、計画が 3 ms、
残りが実行前後のスナップショット・レポートの読み取り・履歴と成果物の書き込み。

suite を 2 つ同時に走らせても 1,145 ms とほとんど変わらない。この fixture では Vitest の suite が全体の 95% を占め、
並べる相手の Bun が 10 ms しかかからないためである。

### worker 数の設定のほうが大きく効く

Vitest を既定の worker 数（コア数分）で直接実行すると 398 ms、worker 1 では 1,131 ms だった。
testry は suite の `workers` を `--maxWorkers` としてランナーに渡すので、**`workers = 1` と書くと、何も指定せずに
直接実行するより遅くなる**。これはオーケストレーションの負荷ではなく設定の結果であり、最初の試走ではこの差
（約 0.7 秒）をオーケストレーションの負荷と取り違えかけた。
`workers` と `cpu_slots` は、そのマシンで実際に使わせたい並列度に合わせて設定する必要がある。

### 実行対象を減らした効果

同じ 1 モジュールの変更に対して、`testry test`（affected）は 39.8 ms、`testry verify`（full）は 1,144 ms だった。
差は約 29 倍だが、これは**実行するテストが 60 ファイルから 1 ファイルに減ったことの効果**であって、
Rust で書いたことの効果ではない。また affected は advisory であり、品質ゲートの代わりにはならない。

逆に、対象が 1 ファイルだけのときは testry の固定費が目立つ。ランナーを直接起動すれば 2.1 ms で済むところ、
testry 経由では 39.8 ms かかる（計画、バージョン確認、実行前後のスナップショット、成果物と履歴の書き込み）。

## 計測していないもの

- **実プロジェクト**。上の値はすべて合成リポジトリのもので、テストの中身が軽く、import も単純である。
- **Storybook / Playwright の suite**（ブラウザの起動時間が支配的になる。M3 の検証時にデバッグビルドで 3 回だけ
  測った値は、story 2 件の suite が 1.7〜2.0 秒、E2E 3 件の suite が 0.9〜1.2 秒だった。ベンチマークとしては未実施）。
- **コンテナ環境の準備**（イメージのビルド、依存のインストール、Dev Container の作成）。testry はそれを行わない（ADR-0006）ので、
  仕様 20 章の比較対象 4（Host と Colima の比較）は対象外。
- **キャッシュが冷えた状態**、他のプロセスと CPU を取り合う状況、キュー待ち（この計測では常に 0）、
  最初の失敗までの時間（失敗するテストを含めていない）。
- **linux-x86_64 や他のマシン**。1 台（Colima の VM）での計測であり、絶対値は環境によって変わる。
- 30 回という回数は p95 を安定して見積もるには少ない。p95 は目安として扱うこと。

## 仕様 20 章の合格条件との対応

| 条件 | 状況 |
|---|---|
| 必須 fixture で予定された影響テストの取りこぼし 0 件 | 受け入れテスト G01〜G18・P01〜P16 で検証（`docs/acceptance.md`）。この計測の合成リポジトリでも、変更したモジュールのテストが選ばれている |
| 不確実性の fixture では必ず fallback または明示的エラー | G06・G07・G12・G17、P02 で検証 |
| キャンセル後に managed process が残らない | R05・R06・R15 で検証（プロセスグループ外に出たものを含む）。container は対象外（ADR-0006） |
| base / dirty / input を正しく識別し、誤った pass 再利用をしない | G08〜G11、P13 で検証。結果のキャッシュは存在しない |
| 実際の性能を raw データ付きで記録する | 本書と `docs/benchmarks/` |
| 全体性能向上と、機能削減による見かけの向上を区別する | 上の「オーケストレーションの追加負荷」と「実行対象を減らした効果」を分けて記載 |
